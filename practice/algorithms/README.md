# Algorithm problems

Interview-style data structures and algorithms problems. Each one is a timed session: you write a
`Solution` class in the editor, **Run** checks it against the examples, and **Submit** also runs
the hidden tests. The review afterwards shows the hints and a full explanation with diagrams,
which includes the commented reference solution.

`foundations/` holds the study pages (approach, complexity, data structures, patterns, dynamic
programming). [docs/writing-content.md](../docs/writing-content.md) covers the markdown, links
and diagram syntax shared with the system design material.

## A problem folder

```
algorithms/a40_reorder_list/
  problem.json      metadata
  statement.md      the problem as an interviewer would give it, with examples and constraints
  hints.md          three or four hints, each giving away a little more
  explanation.md    the walkthrough: brute force, the insight, the optimal solution, diagrams
  solution.py       the reference solution, commented; the explanation shows it
  cases.py          the test inputs (and a brute-force solution to check the reference)
  checker.py        only when several answers are correct (see "compare" below), with
  checker.js          the same check in JavaScript, for Java and C++ solutions
  tests.json        generated by tools/build_algo.py; don't edit it
```

After changing `cases.py` or `solution.py`, rebuild:

```sh
python tools/build_algo.py a40_reorder_list
python tools/check_content.py algorithms
python -m ruff check algorithms/a40_reorder_list
python -m ruff format algorithms/a40_reorder_list
```

`ruff format` also formats the ```` ```python ```` blocks inside the markdown files, so keep the
code in explanations runnable and ruff-clean.

`build_algo.py` computes the expected outputs with `solution.py`, checks them against `brute()`
on every case and on random ones, writes `tests.json`, then runs the reference through the real
test runner (it must pass everything), runs the empty starter code (it must fail something) and
checks the markdown's diagrams.

## problem.json

```json
{
  "id": "a40_reorder_list",
  "number": 40,
  "title": "Reorder List",
  "difficulty": "Medium",
  "patterns": ["Linked lists", "Fast and slow pointers"],
  "signature": "def reorderList(self, head: ListNode | None) -> None:",
  "adapters": {"args": ["listnode"], "check": "arg0"},
  "foundations": ["patterns/linked-list-techniques", "data-structures/linked-lists"]
}
```

| Key | Meaning |
|---|---|
| `id` | the folder name: `a` + two-digit number + `_` + snake_case title |
| `number` | position in the list |
| `difficulty` | `Easy`, `Medium` or `Hard`. Sets the time target: 20, 30 or 40 minutes |
| `minutes` | optional: override the time target |
| `patterns` | short tags shown on the card ("Hashing", "Two pointers", "Dynamic programming") |
| `signature` | the method the solver writes, exactly as it appears in the Python starter code. The Java and C++ versions are generated from its types, so use only `int`, `float`, `bool`, `str`, `list[...]`, `tuple[...]`, `X \| None`, `ListNode`, `TreeNode` and `Node` (built-in spellings: not `typing.List`/`Optional`, which the linter flags) |
| `java_return` | optional: the Java return type, when the generated one isn't the usual choice. A list of numbers returns an array and other lists a `List`, so interval problems set `"int[][]"` |
| `records` | optional: a Java record for each tuple type, which Java doesn't have: `{"tuple[int, list[str]]": "Sample(timestamp, stack)"}`. C++ uses `pair` and `tuple`. The build says when one is missing |
| `adapters` | optional: linked list, tree and graph arguments (below) |
| `compare` | optional: `exact` (default), `unordered`, `unordered_nested` or `validator` |
| `foundations` | foundations sections to review, as `"page/section"` (listed below) |

### Linked lists, trees and graphs

Tests are written in plain lists. `adapters` says which arguments are really linked lists,
trees or graphs; the runner builds them before the call and turns the result back into a list.

| Kind | Test notation | The method receives |
|---|---|---|
| `listnode` | `[1, 2, 3]` | the head `ListNode` (or `None` for `[]`) |
| `listnodes` | `[[1, 4], [2, 6]]` | a list of heads (arguments only) |
| `tree` | `[3, 9, 20, null, null, 15, 7]` (level order; `None` in Python) | the root `TreeNode` |
| `graph` | `[[2, 4], [1, 3], [2, 4], [1, 3]]` (node `i+1`'s neighbours) | node 1 (`Node` with `val` and `neighbors`) |

```json
"adapters": {"args": ["tree", null], "result": "tree"}
```

- `args` lists a kind (or `null`) per argument; `result` converts the return value.
- `"check": "arg0"` is for methods that change their input in place and return `None`: the test
  compares the first argument after the call instead of the return value.
- With a `graph` argument and a `graph` result, the runner also checks the result shares no
  node with the input (a real deep copy).
- A `graph` is connected and numbered 1 to n, and the method gets node 1. A `graph` result is
  compared neighbour list by neighbour list, in order, so the statement must say to keep each
  node's neighbours in their original order.
- The starter code includes the node classes, and the runner builds inputs with the solver's own
  classes, so `isinstance` and type hints work.

### compare

| Value | Use it when |
|---|---|
| `exact` | there is exactly one right answer (tuples count as lists) |
| `unordered` | the answer is a list whose order doesn't matter (Top K, Two Sum's indices) |
| `unordered_nested` | a list of lists where neither order matters (Group Anagrams, 3Sum) |
| `validator` | several different answers are right (any valid course order, any longest palindrome) |

For `validator`, write `checker.py`:

```python
def check(args, expect, actual):
    """args: the test's arguments; expect: the reference's answer; actual: the solver's
    (converted to plain lists). Return True, False, or a message explaining the failure."""
    (s,) = args
    if not isinstance(actual, str) or actual not in s:
        return "Return a substring of s."
    if actual != actual[::-1]:
        return f"{actual!r} is not a palindrome."
    return len(actual) == len(expect)
```

and `checker.js`, the same check for Java and C++ answers, which the app judges in JavaScript
(`static/judge.js`). It gets the same plain values, with `null` for `None`:

```js
function check(args, expect, actual) {
  const [s] = args;
  if (typeof actual !== "string" || !s.includes(actual)) return "Return a substring of s.";
  if ([...actual].reverse().join("") !== actual) return `${JSON.stringify(actual)} is not a palindrome.`;
  return actual.length === expect.length;
}
```

`build_algo.py` refuses a `validator` problem without both files.

## cases.py

```python
import random

# Each case is a tuple of arguments, or a dict:
#   {"name": "...", "args": (...), "expect": ..., "limit_ms": 1000}
# Without "expect", the reference's output is used. Give "expect" for the statement's examples,
# so a wrong reference is caught.
SHOWN = [
    {"name": "Example 1", "args": ([1, 2, 3, 4],), "expect": [1, 4, 2, 3]},
    {"name": "Example 2", "args": ([1, 2, 3, 4, 5],), "expect": [1, 5, 2, 4, 3]},
]

HIDDEN = [
    {"name": "empty list", "args": ([],)},
    {"name": "one node", "args": ([7],)},
    ([1, 2],),
    {"name": "10,000 nodes", "args": (list(range(10_000)),), "limit_ms": 1000},
]


def brute(values):
    """Obviously correct, slow is fine. Takes the plain-list arguments; returns the plain answer."""
    ...


def random_cases(rng: random.Random):
    """Small random inputs (yield argument tuples); each is checked against brute()."""
    for _ in range(200):
        yield ([rng.randint(-9, 9) for _ in range(rng.randint(0, 9))],)


def naive(values):
    """Optional: the plausible but too-slow solution (often the O(n^2) one). The build checks
    that every limit_ms test rejects it. Without naive(), brute() is used."""
    ...
```

- **Shown** tests are the examples (2 to 4). The solver sees them and Run executes them.
- **Hidden** tests (8 to 15) run on Submit. Cover the edge cases (empty and single-element inputs,
  duplicates, negatives, all equal, already sorted, the answer at either end...) and one or two
  large inputs with a `limit_ms`.
- **Large inputs** catch a too-slow algorithm. Choose a size where the reference takes a few ms
  and the naive approach takes well over a second (for O(n²) loops, n of about 20,000 to
  30,000), make the input adversarial (put the answer at the end, where a scan finds it last),
  and set `"limit_ms": 500`. The build warns when `naive()` (or `brute()`) beats the limit, or the
  reference takes more than a tenth of it. Keep each input under about 100 KB of JSON (small
  values help) and make it deterministic (`random.Random(seed)`).
- **Write `naive()` the way a solver would.** A quadratic loop that hides its inner loop in a
  built-in (`x in nums[i + 1:]`, `nums.count(x)`, `max(nums[i:j])`) runs at C speed, roughly
  ten times faster than the same loop written in Python. Make `naive()` that shortcut, not a
  Python double loop, and size the large inputs so that it still fails.
- **A time limit can't separate every pair.** An O(n) scan done by a built-in
  (`nums.index(target)`) finishes a 100 KB input in well under a millisecond, so no `limit_ms`
  rejects it in favour of an O(log n) search. For those problems, use the large inputs to test
  correctness only, and say in the explanation that the interviewer expects the faster algorithm.
- **Timing is noisy.** The build's timing warnings come from single runs, so they can appear
  when the machine is busy (for example while other builds run). Rerun the build before changing
  the sizes or limits.
- **Solutions run in the browser.** The build checks the reference natively, but the app runs it
  in Pyodide, which is up to about twice as slow (the tenth-of-the-limit margin covers that), has
  no threads, and stops on recursion through built-in code past a few hundred levels (see the
  README). After building, run `tools/build_static.py` and then
  `node --test tests/js/references.test.mjs`, which runs every reference on every test there.
- Single-argument cases need a trailing comma: `([1, 2, 3],)`.
- `brute()` and `random_cases()` are optional but strongly recommended. `brute()` runs on every
  test without a `limit_ms`, so a large test without a limit needs a `brute()` that finishes on
  it (polynomial, not exponential).
- Values must be JSON: lists, numbers, strings, booleans, `None`. Tuples become lists.

## The markdown files

Don't start a file with a `#` title; the app shows the problem's title.

**statement.md**: the problem in plain words, then the examples (`Input:` / `Output:` in a code
block, a sentence explaining each), then **Constraints**. Use the argument names from the
signature. A data-structure diagram of an example helps for lists, trees and grids.

**hints.md**: three or four hints as `**Hint 1.**` paragraphs, from a nudge to nearly the answer.
Hints are never shown during a session, so they can link to foundations sections.

**explanation.md**: a complete walkthrough with `##` sections, roughly:

1. **Understand the problem**: restate it, work an example, note edge cases.
2. **Brute force**: what it is and its complexity.
3. **The key insight**: what makes it faster, with diagrams of the idea in action (array
   pointers moving, the tree being walked, the DP table filling, the heap's contents...).
4. **The solution**: an empty ```` ```solution ```` block, which the app replaces with
   `solution.py` (don't paste the code here: there is one copy, the commented one), then why it
   works and what to watch for. Exactly one marker per explanation; `check_content.py` and
   `build_algo.py` fail without it.
5. **Complexity**: time and space, with the reasoning.
6. **Pitfalls and variations**: edge cases that break naive code, and follow-up questions.

Link to foundations sections where they explain a technique, e.g.
`[sliding window](#/algo/learn/patterns/sliding-window)`.

**solution.py**: `class Solution` with the method from `signature`, plus any helper methods.
Comment it for a reader learning the technique: it is the only copy of the solution the review
shows, inside the explanation. Python standard library only.
