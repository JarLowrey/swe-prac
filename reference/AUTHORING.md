# Authoring a problem package

Everything in `reference/` is a spoiler. The app reads only `problems/<pid>/`. The reference
solution is shown on the post-session review screen, never during a session.

## Layout

```
problems/<pid>/
  problem.json            id, number, title, summary, class_name, levels[{level, title, methods}]
  statement/level1.md     one file per level, shown when that level unlocks
  statement/level2.md ... level4.md
  review/hints.md         design hints (post-session only)
  review/analysis.md      solution analysis (post-session only)
  tests.json              GENERATED by tools/build_problem.py, do not edit
  stubs.json              GENERATED (method stubs per level, from the reference signatures)
reference/<pid>/
  solution.py             reference solution
  tests.txt               test source (shown + hidden), see format below
  gen.py                  random sequence generator used by `@gen` tests
  mutants/*.py            deliberately buggy copies of solution.py
```

Build and verify: `.venv/Scripts/python tools/build_problem.py <pid>` (or `--all`). It must print `OK`.

## problem.json

```json
{
  "id": "p1_file_store", "number": 1,
  "title": "In-memory file store",
  "summary": "One sentence saying what to build. No mention of later levels or the crux.",
  "class_name": "FileStore",
  "levels": [{"level": 1, "title": "Basic files", "methods": ["add_file", "get_file_size", "delete_file"]}, ...]
}
```

Every public method of the reference class must appear in exactly one level.

## Statements (`statement/levelN.md`)

Markdown. The UI shows the level title and the shared conventions (`problems/conventions.md`)
itself, so do not repeat those. Rules:

- `level1.md` opens with a 1-3 sentence intro saying what is being built. It must **not** hint at
  later levels, twists or the crux (those go in `review/analysis.md`).
- Each method is a bullet: ``- `add_file(timestamp, name, size) -> bool` adds a file. Returns `False` if ...``
  followed by any extra rules as plain bullets or short paragraphs.
- Python terms: snake_case names, `None`/`True`/`False`, `int`/`str`/`bool`, `int | None`,
  `list[tuple[str, int]]`, `math.inf`. Never mention TypeScript, `null`, `Map`, `number`.
- Keep the source doc's wording and every rule it states; do not add rules the doc does not state.
- A level must not reveal later levels. Where a later level changes earlier behaviour, say so in
  the later level's statement (e.g. "Changed behaviour: `search_available` now ...").

## Reference solution (`reference/<pid>/solution.py`)

- One class named `class_name`, no-arg constructor, standard library only.
- Public methods are exactly the problem.json methods. First parameter after `self` is `timestamp`;
  other parameter names match the statement. Fully type-annotated.
- Each public method has a one-line docstring describing its behaviour **using only information
  from that method's own level statement**. It is copied into the user's starter stubs.
- Helpers are private (`_name`). Code should be clean, idiomatic and readable: it is shown to the
  user as a model answer after the session. `ruff check` must pass.

## Test source (`reference/<pid>/tests.txt`)

```
=== L1 shown: basic add, get, delete
add_file(1, "/a.txt", 10) -> True
add_file(2, "/a.txt", 5) -> False      # comment
add_file(3, "/b", 1); add_file(4, "/c", 2)
get_file_size(5, "/b") -> ?

=== L2 hidden: long random sequence @gen(seed=7, n=300)
```

- Each `===` block is one test and runs on a **fresh instance**. Header:
  `=== L<level> <shown|hidden>: <name>` with an optional trailing `@gen(seed=.., n=..)`.
- Steps are Python calls with literal args. `-> literal` checks the value by hand, `-> ?` takes the
  expected value from the reference solution, and no arrow means unchecked (it must still not raise).
- The first argument (timestamp) must strictly increase within a test.
- A level-N test may call methods from levels 1..N only.
- Tuples in args (e.g. order lines) are passed through as real tuples.
- Every level's gate is: all shown and hidden tests of levels 1..N pass. So level-N tests run against
  the user's final code too.

Shown tests are public: the app renders them as the read-only `tests.py` tab (grouped by level, only
for unlocked levels), and the first Level 1 shown test also seeds `scratch.py` as an example case.
Nothing to author for that, but a shown test's name and calls are what the user reads, so keep
names descriptive and keep shown tests free of anything the statements don't say.

Quotas per level: the doc's self-check test (keep as-is) plus **2-3 extra shown tests**, which are
small and illustrative with hand-written expectations. Then **8-12 hidden tests**:
- edge cases with hand-computed expectations (prefer explicit values over `?` for these)
- at least one test where the new level's feature interacts with earlier-level methods
- tie-breaking and ordering, invalid inputs leaving state untouched, and ids/counters not consumed
  by failures, wherever the spec defines them
- at least one `@gen` random test (n = 150-400)

Only test behaviour the statement pins down. If the spec is ambiguous, don't test it, and list it
in your report.

If a hand-written expectation disagrees with the reference, decide from the spec which one is
wrong and fix that one. The doc's self-check tests are ground truth: never edit their expectations.
If one looks wrong, report it.

## Generator (`reference/<pid>/gen.py`)

```python
def generate(level: int, rng: random.Random, n: int) -> list[str]:
    """Return n DSL call lines (no arrows) using only methods of levels <= level."""
```

Mix valid and invalid operations. Keep id/name spaces small (3-6 values) so collisions, ties and
re-use happen often. Timestamps strictly increase (random gaps are fine and help TTL/expiry logic).
Every line is checked against the reference automatically.

## Mutants (`reference/<pid>/mutants/*.py`)

4-6 files. Each is a full copy of `solution.py` with **one** realistic bug. Draw from the doc's
"common mistakes" and crux, plus off-by-one, tie-break and failed-op-consumes-id bugs. Start each
with a docstring naming the bug. The build fails unless every mutant fails at least one **hidden**
test, so this is how you show that the hidden suite has teeth.
